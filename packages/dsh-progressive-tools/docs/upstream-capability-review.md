# 上游能力与继续维护评估

> 历史评估：下文的兼容失败结果对应升级前的 `f2bd297`，不是当前版本状态。
> `0.4.0` 已完成 `0.1.5-rc.1` 适配，完整检查和 46 项测试通过，并新增
> PTC/both 双语言 SDK 与真实绑定管线回归。解释器与真实任务收益仍未实测。
> 当前使用要求见[升级指南](migration.md)，验证范围见[测试说明](testing.md)。

评估日期：2026-09-13。评估基线：本仓库 `f2bd297`，版本 `0.3.0`。

## 判断

建议保留项目，集中投入一轮新版兼容和收益验证，暂缓扩大功能范围。
上游已经提供工具限制、程序化调用、请求头管理和完整执行管线，但在本次
核对的主分支与默认发布包中，没有发现内置的等价搜索与稳定分发实现。
本项目仍填补“首个请求精简，发现后工具定义和系统前缀不变”的缺口。

这个缺口不等于已经证明商业或性能收益。当前版本不能直接视为兼容最新
运行时，且缺少真实任务成功率、缓存命中、耗时和总成本对照数据。
适合有大量插件工具、长会话、多轮任务的部署；工具很少或会话很短时，
额外搜索和间接调用可能抵消收益。

## 仓库结构与责任

| 文件 | 核心责任 | 维护判断 |
| --- | --- | --- |
| `src/index.ts`（1066 行） | 配置、搜索与分发注册、最终请求投影、guard、会话恢复、生命周期 | 核心差异化也集中在此；新版兼容优先于拆分 |
| `src/catalog.ts`（298 行） | 显式分组、自动前缀分组、BM25 风格排序、中文等文本 bigram、schema 搜索 | 可独立保留；需要真实查询集和规模基准 |
| `src/state.ts`（153 行） | dynamic 模式的工具族激活、LRU、轮次过期、预算与快照 | 兼容负担；建议冻结新增功能 |
| `src/defaults.ts`、`src/types.ts` | 默认工具面、工具族规则、公共配置与结果协议 | 配置属于公共兼容面 |
| `tests/catalog.spec.ts`、`tests/state.spec.ts` | 目录与动态状态算法 | 升级实验仍通过 |
| `tests/plugin.spec.ts` | 首次投影、发现提交、分发、恢复、卸载 | 需随运行时接口迁移 |
| `tests/agent-loop.spec.ts` | 实际请求捕获与搜索前后工具、系统文本相等断言 | 值得保留并扩展的关键资产 |
| `cordis.patch.yml` | 插件组合入口 | 安装与热重载回归的一部分 |

默认流程：完整目录留在进程内，`tool_search` 将命中定义追加到历史，
`tool_dispatch` 以父调用 token 进入原工具执行管线。guard 阻止延迟名字
直接调用；搜索成功后提交发现状态，通过结果元数据或日志恢复。
`dynamic` 则在搜索后改变原生可见工具集，不能提供同样的前缀稳定保证。

## 上游是否已覆盖

| 能力 | 上游当前情况 | 本仓库剩余价值 |
| --- | --- | --- |
| 工具注册、参数校验、审批扩展、guard、执行包装 | 已有 | 复用即可，不应重复实现 |
| 按 agent 限制工具 | 已有 `restrict()`，限制取交集，作用域本地工具保留 | 上游提供基础机制，并未直接实现搜索策略 |
| PTC / `run_code` | 已有，SDK 从可见工具生成 | 减少顶层原生 schema 数不等于移除全部工具描述成本 |
| 工具排序与请求头记录 | 已有 | 工具变化仍被识别为请求头变化，不等于发现时前缀不变 |
| 按需搜索完整目录并返回精确定义 | 本次核查未发现内置实现 | 搜索与分组策略仍有用途 |
| 搜索后保持小工具面和 SDK 不变 | 本次核查未发现等价内置机制 | 默认模式的主要价值 |
| 延迟工具经固定代理调用且禁止直接绕过 | 执行基础能力已有，未见此策略内置 | 路由一致性与回归测试仍有价值 |
| 中文查询、工具族发现、Skill 联动 | 未见等价内置组合 | 实际效果尚需任务集验证 |

源码证据均对应上面的固定上游提交：

- `packages/core/tools/README.md`：`mode`、限制语义、PTC token 与缓存边界。
- `packages/core/tools/src/index.ts`：`sdkSection()` 从当前可见工具生成 SDK；
  `restrict()`、`guard()` 和 `schemas()` 提供公共机制。
- `packages/core/system-prompt/src/index.ts`：先收集 schema，再进入
  `system-prompt/assemble`；完整提示覆盖会在 waterfall 后重新生效。
- `packages/core/agent-loop/src/agent.ts`：`toolsChanged()` 比较当前工具与
  已记录请求头，`buildRequest()` 记录变化后的 header。
- `docs/cookbook/extension-cookbook.md`：将渐进式披露列为使用 scoped
  restriction 实现的扩展方式。
- 全库搜索工具搜索、分发和原生延迟字段，并检查工具注册及请求构造路径；
  缺席判断限定于本次固定版本，不代表上游未来没有计划。

生态方面，`vibeinging/dsh-tool-search` 的维护者文档描述了搜索后扩展
原生 schema 的外部实验插件；`Letter2025/dsh-tool-search` 描述了
搜索、描述、调用桥接及 warm-tool 动态注入。二者证明需求已有其他解法，
但不能直接据此认为本项目的稳定前缀保证已被替代。本次仅阅读这些项目的
维护者文档，未安装、测试或认证它们的兼容性与安全性。

## 实测兼容性

原仓库运行 `pnpm run check`：类型检查、lint、40 项测试、构建和
publint 全部通过。这证明当前已安装依赖基线可工作。

另建临时副本，复制源码、测试与构建配置，将已有核心 peer/dev 依赖统一
固定为 `0.1.5-rc.1`，执行 `pnpm install --ignore-scripts`，随后分别
运行 `pnpm run typecheck` 和 `pnpm run test`。未改原仓库依赖与锁文件。

结果：类型检查失败；测试 19 通过、21 失败，4 个测试文件中 2 个失败。
这些不是 21 个独立缺陷，主要集中于少数接口变化及旧测试夹具。

| 证据 | 影响与迁移方向 |
| --- | --- |
| `src/index.ts:12` 的 `CallId` 不再导出 | 调用 ID 需迁移至新版 `ToolCallId` / brand 公共入口 |
| `src/index.ts:18` 的 `JsonValue` 不再由工具包导出 | 重新核实值类型归属，避免依赖传递导出 |
| `src/index.ts:530`、`:574` 使用 `session.events` | 新版提供 `snapshotEvents()`；实际测试在 `.reduce` 处失败 |
| `src/index.ts:615` 只识别 `tool/code-dispatch` | 新版使用 `tool/ptc-dispatch`，恢复逻辑需要迁移并考虑旧日志 |
| 真实循环测试同步调用 `agentLoop.create()` | 新版返回 Promise，需调整初始化及新服务组合 |
| 依赖声明引用 attachment 类型但无法解析 | 此次安装图另有类型依赖问题，应与插件源码错误分开处理 |

主分支源码确认上述新会话 API、调用 ID 和 PTC 事件存在。`context.agent`
仍由 agent 包扩展到组装上下文，不能误判为已删除。

当前测试未实际覆盖完整 PTC 运行时下的 TypeScript/Python SDK 前缀稳定、
真实程序嵌套执行和 compaction 后恢复。已有嵌套日志测试采用手工追加旧
事件的方式。它们是迁移验收重点，不能用当前 40 项通过代替。

## 后续投入建议

1. **先做兼容版本。** 迁移调用 ID、值类型、会话快照与 PTC 事件，更新真实
   AgentLoop 夹具和必要依赖。明确支持的版本区间，分别验证默认发布和 next。
   旧日志回放、卸载重载、其他工具限制和作用域隔离必须保留。
2. **补关键执行测试。** native、PTC、both；两种 SDK 语言；首个请求与发现
   后的前缀；参数校验、审批拒绝、取消、非文本结果、嵌套调用与真实恢复。
   特别检查 complete-prompt 组合是否保留可理解的发现指引。
3. **做有限规模对照。** 固定 10/50/200 工具及少工具、多工具任务集，对比
   原生、PTC、stable-proxy，记录任务成功率、检索召回、总 token、实际
   缓存命中、额外调用次数、耗时与成本；以相同任务和配置重复测试。
   字符数估算及结构前缀相等不是实际缓存命中或账单节省的证据。
4. **只按数据优化。** `searchTools()` 每次重建文档，并在候选与查询词循环
   内重复统计全目录词频，规模增大可能放大成本。若基准确认为瓶颈，再缓存
   分词、文档频率和索引；不先引入向量服务或重排依赖。
5. **控制范围。** dynamic 模式优先修兼容问题，停止扩大配置；不要同时维护
   多套搜索架构。可在兼容完成后将投影、恢复和分发从入口拆分，降低改动风险。

继续投入的条件：真实目标部署确有大目录需求，兼容迁移可控，并且实测在
成功率可接受的前提下减少总成本或改善耗时。若工具规模长期很小、收益不足，
转维护模式；若上游以后提供等价稳定披露机制且满足本项目关键回归，优先
迁移或贡献实现，再考虑归档。当前证据不足以支持立刻归档，也不足以支持
大规模扩展。

本评估最初仅记录调研结论；后续适配和发布工作以变更记录及版本标签为准。
