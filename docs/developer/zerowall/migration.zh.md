# 逐步迁移原 ZeroWall 功能

[English](migration.md) | 中文

## 概述

每次迁移一个可用功能，同时保持当前桌面可安装、可启动。先盘点原实现，再选择仓库与依赖。每次迁移包含用户入口、Host 行为、测试、打包证据，以及需要时的数据安全转换。以下批次是开发顺序，不表示相关功能已经迁移。

<a id="inventory"></a>

## 1. 盘点单个功能

阅读原项目 `plugins/` 中该功能、对应 `packages/`、profile 补丁和既有测试。记录旧包与入口，不复制整个 workspace。将以下清单写入功能 Issue 或迁移 PR。

- 用户入口与一个可观察的成功场景；所需设置与权限。
- Host 服务、客户端插槽、远程方法、npm 依赖、子进程、网络服务及共享存储。
- 持久化文件或表、新旧版本、凭据归属、迁移可逆性及备份路径。
- 运行时资源、许可证、体积、支持平台、失败恢复、测试负责人与验收负责人。

<a id="batches"></a>

## 2. 选择迁移批次

根据用户价值与依赖成本选择下一个功能。下表中的源码名称用于盘点候选功能；确定顺序前核实实际耦合。

| 批次 | 原项目候选 | 完成标准 |
|---|---|---|
| 保持基线可用 | 已集成的账户、secrets、AI Cloud、Brand UI | 登录、模型、云调用与安装器检查持续可用。 |
| 独立业务流程 | `pubmed`、`mineru`、`publications`、`zotero-harvest`、`dsh-file-review` | 每次选一个流程，独立安装并完成一次真实任务。 |
| 科学共享数据 | `projects`、`research-store`、`research`、`files`、`runs` | 先明确数据归属、导入和备份，再迁移依赖的界面。 |
| 受管理的执行环境 | `environment`、`execution`、`python`、`mcp`、`singlecell` | 验证外部运行时获取、取消、失败处理和资源清理。 |
| 其他媒体与集成 | `images`、`videos`、`dsh-ppt-maker`、`wechat` | 补充剩余用户流程，复用现有云服务。 |

<a id="implementation"></a>

## 3. 完成插件实现

新插件也只保留一个固定目录，在该插件仓库的 `main` 开发。共享同一生命周期并一起发布的功能可以合并；可独立替换的能力保持分离。窗口、安装器和系统集成留在桌面；业务功能使用已有 Cordis 服务、远程方法、工具和客户端插槽。

去掉只能在旧单仓解析的依赖，包括 `workspace:*`、源码别名和绝对资源路径。必要的共享库明确发布，紧密耦合的私有辅助模块可随插件打包。DSH 与 Cordis peer 版本应兼容目标桌面。导出构建后的声明，随包携带客户端图标；只有需要安装为 profile 层时才声明 `dsh.bundle.patch`。

实现功能时一并设计错误状态与释放：提供可处理的错误提示，停止依赖工作，并释放监听器、计时器、子进程和临时文件。凭据继续使用既有凭据服务。模型可见的输入与结果必须能从 Session 事件重建；纯 UI 夹具放在所属目录。遵循[架构](../../architecture.zh.md)和[测试策略](../../testing.zh.md)。

<a id="data"></a>

## 4. 保护既有数据

在旧数据的副本上测试导入与迁移，记录来源版本、导出／导入步骤、备份和导入后检查。不要覆盖原 profile，不把明文密码复制到配置，也不要把插件降级当作数据库自动降级。

涉及已发布 Session 或已声明持久化类型的变更，遵循[持久化评审流程](../../cookbook/reviewing-persistence-type-changes.zh.md)与 [Session 格式状态](../../session-format-status.zh.md)。保留已提交的历史数据代际，SQLite schema 版本只能递增。对外可感知的破坏性变更应写[升级指南](../../../.agents/skills/dsh-create-upgrade-guide/SKILL.md)。不要宣称读取器并未实现的回退兼容。

<a id="acceptance"></a>

## 5. 验收并集成一个批次

功能独立测试通过后，按[开发集成步骤](development.zh.md#integration)接入桌面。每个批次记录以下结果，才能视为已迁移。

1. 独立类型检查、单元测试、构建产物及打包消费者导入通过，不依赖旧 workspace。
2. 在隔离的目标 DSH profile 从公开 Git 源安装，重启并完成所选用户任务。
3. 禁用或卸载后确认注册和后台任务停止；重新安装或升级不丢失该功能的数据。
4. 覆盖失败与取消，为模型可见行为提供无密钥 Session 回放，为界面提供所属目录的证据。
5. 新增运行时资源、原生依赖或桌面壳集成时，完成 Windows 打包与干净机器检查。
6. 先提交插件，再提交桌面固定版本、锁文件和适用的市场元数据；附验收证据与已知限制。

<a id="distribution"></a>

## 6. 分发与恢复

DSH Discover 通过 `market/index.json` 列出 npm 发行包和历史固定 Git 源。ZeroWall 签名资源目录单独验证目录签名、不可变归档摘要和兼容性。完成 preview 验证后才能晋升稳定目录。单独更新 Discover 不等于发布或验证签名资源目录。

保留前一个插件提交、桌面锁文件、安装包和数据备份。仅代码回归时，在新的桌面提交中恢复已知可用的固定版本并重新测试。涉及数据格式变更时，使用已测试的导入／恢复步骤；用兼容版本的程序读取，不能让不支持的旧读取器打开迁移后的数据。
