# 上下文、缓存、提示词与 MCP 按需加载方案（8.4.18）

## 诊断结论

本轮以 `session.v4.jsonl`、请求日志和截图中的实际请求为准。一次请求曾携带 186 个工具定义，Schema JSON 约 161,896 字符；MCP 注入后增至 220 个、约 212,029 字符。初始输入约 38k tokens，系统消息约 10k–14.6k 字符。工具定义和长系统提示词共同解释了“工具上下文约 4k”以及首轮输入突然升高，并非模型推理强度造成。

缓存不是固定开关。日志中后续请求出现 39k–51k 的缓存读取；当工具集合从 186 变成 220 时，前缀发生变化，缓存读取降为 0，未缓存输入回到约 40k。缓存按请求前缀命中，系统消息、工具 Schema、路由和历史顺序任一变化都可能使该次前缀失配。应用只能通过稳定前缀和减少动态注入提高命中，不能强行要求网关命中。

截图中的 `contextWindow=262144` 是当前模型的容量，不是用户预算。用户预算默认 300k 时，有效预算取 `min(用户预算, 模型窗口)`；还要扣除输出预留和 16k 安全余量，压缩压力阈值为：

```text
min(有效预算 × 90%, 模型窗口 - 输出预留 - 16k)
```

因此 262k 模型上设置 300k 不会得到 300k 的实际输入空间；1m 网关模型可以使用更大的有效预算。GPT、Claude、DeepSeek 以及其他提供商均走同一容量解析：网关模型目录优先，缺字段时使用本地 `models.dev` 快照，仍无法确认的私有模型保持未知，不猜测窗口。

## 8.4.18 已实施的运行策略

### 1. 常驻工具降到 DSH 基础面

`plugin-base` 在工具表超过 32 个时，为当前 Agent 建立 scoped allow-list。常驻只保留 DSH 的文件、Shell、Web、Skill、计划、任务和目标工具，以及 `capability_search`。MCP、Research、R 文件、Python 环境等 ZeroWall 专用工具不再默认进入大工具表；模型先检索能力，再按精确名称一次最多启用 12 个工具。启用集合只属于当前 Agent，不会泄露给其他对话。

这解决了“动态加载已经存在但 4k 工具定义仍然出现”的原因：此前 ZeroWall 路由工具也在基础白名单中，动态限制并没有真正移除它们。

### 2. 系统提示词拆分

常驻 ZeroWall 提示只保留产品身份、科学结果真实性、权限/凭据/来源边界、附件不可信和能力检索入口。Web 搜索、Zotero、媒体创作、Biomni、R 工作流、Windows 操作规则和完整 Python 规范不再拼进每轮固定提示；它们分别由 DSH 原生工具、Skill、MCP 实时 Schema 或按需资源提供。媒体插件不再注册长 `systemPrompt.context`，详细规则只在 `media-create` Skill 被加载时出现。

### 3. MCP 连接和 Schema

启动阶段只读取连接记录和短索引，不启动全部服务器。`mcp_search` 按服务器名、显示名、内置功能词和索引摘要模糊匹配，只选择已启用或内置 RMCP 记录；选中后才对该服务器执行实时 `tools/list`，并仅把实时语义命中的工具加入当前 Agent。服务器名命中但没有工具命中时只返回候选摘要，不加载前 8 个无关工具。MCP Schema 仍受权限、凭据、运行时健康和原始工具守卫约束。

内置 RMCP 的正式名是 `rmcp`。旧路由名 `zerowall-rmcp` 会迁移到 `rmcp`；旧别名也能被 `mcp_connect` 识别。若实际请求 R/FAERS 能力时发现内置 RMCP 记录缺失或被停用，Host 只修复并启用这个内置记录，然后刷新实时工具列表；普通用户 MCP 不会被自动唤醒。远端返回的错误与 Host 本地“disabled or unknown”错误现在分开，连接失败会保留远端诊断。

### 4. 工作流参数

`research_task_id` 是可选的本地绑定字段。普通 FAERS、GEO、NHANES 等远程操作不需要它；占位字符串或其他模块误传的非 UUID 值会被忽略。只有真实 UUID 才执行本地任务存在性和工作区归属检查；这样保留了显式绑定的安全边界，同时不把无关字段当成必需条件。R Platform 项目绑定由 Host 按会话稳定生成并复用，用户不需要手填项目 ID。

### 5. 上下文预算 UI 与压缩

设置页和当前对话输入栏均提供 32k–1m、4k 步进的滑块，默认 300k。输入栏显示“请求预算/有效预算”，悬停或无障碍文本同时显示模型窗口和开始压缩阈值。拖动过程中只更新本地控件，指针抬起、键盘调整结束或失焦时保存一次，避免每个滑块事件写入会话。

预算检查读取当前 Agent 的实际 provider/model 和 DSH `resolveModelInfo`；模型容量缺失时只记录诊断，不擅自换模型或缩小输出设置。超过阈值先运行工具结果精简，再按完整工具调用/结果配对选择较早的历史区间进行 DSH 压缩；原始事件保留，最新消息和配对不删除。压缩不是逐 token 拦截器，超大的单条新输入仍可能在下一轮计量前暂时超过预算。

## 验收标准

1. 日志中的大工具场景首个请求只含 DSH 基础工具和 `capability_search`；调用检索后，下一轮只增加精确启用的工具。
2. 未使用媒体、Zotero、Web 搜索、Research、MCP 或 Python 能力时，固定系统提示不包含这些领域长说明。
3. MCP 启动不执行服务器连接；命中某一启用服务器后只刷新该服务器，其他服务器保持 idle；实时工具为空时不注入无关 Schema。
4. `zerowall-rmcp`、缺失的 `rmcp` 和停用的 `rmcp` 在实际 R/FAERS 请求时均能进入同一按需修复路径；普通 MCP 的停用状态保持不变。
5. FAERS 传入占位 `research_task_id` 可以提交；真实 UUID 仍拒绝跨工作区任务。
6. 262k、300k、1m 和未知容量模型分别显示正确的模型窗口、有效预算和阈值；网关容量优先于 `models.dev`。
7. 回归通过后再生成独立插件归档、完整 Stage、ASAR/runtime closure 和 Windows 安装器；不覆盖已发布的不可变归档。

## 可重复诊断

刷新模型容量快照：

```powershell
node tools/models/update-models-dev-context.mjs
```

查看缓存诊断时同时比较 `system_prompt_hash`、`tool_schema_hash`、`skills_hash`、路由摘要、未缓存输入、缓存读取和工具数量；只看缓存百分比无法判断动态工具是否生效。发现工具数量异常时先记录 Agent 的 scoped schema，再检查 `capability_search` 是否启用过额外工具和 MCP 是否发生了实时刷新。
